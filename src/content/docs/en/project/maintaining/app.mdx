The [All Contributors app](https://github.com/all-contributors/app) is the GitHub App that runs the bot you interact with on GitHub. This page helps you understand how it works and how to develop it. It covers how the app is built, how to run it against a test repository, how to test it, and how it is released and deployed.

:::note[Want to learn how to use the app?]
See the [app documentation](/en/app) instead.
:::

## How the app is built

A [GitHub App](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/about-creating-github-apps) is the interface between people on GitHub and the server that processes their requests. It has its own identity (the bot you see in comments), a set of permissions (what it can read and write), and a webhook URL. When someone comments `@all-contributors please add @user for code`, GitHub sends that comment as an HTTP request to the webhook URL, and the server processes it.

The All Contributors app is a [Probot](https://probot.github.io/docs/) application written in JavaScript. Probot receives webhooks, verifies them and authenticates requests to the GitHub API. The app's own code only has to parse comments and update the contributor files. The app uses the [`all-contributors-cli`](https://github.com/all-contributors/cli) package to edit and generate your contributor table. If the generated table looks wrong, there is likely a bug in the CLI repository, rather than the app.

All of the app's logic starts in `app.js`. It does two things:

- **Handles comments.** For every new issue or pull request comment (`issue_comment.created`), it skips comments the bot wrote and comments that don't mention the bot, then processes the rest.
- **Logs installs.** When someone installs or uninstalls the app (`installation` and `installation_repositories`), it logs the account and how many repositories changed.

The same `app.js` can run in two places. On your computer, running `pnpm start` runs it locally with Probot. On Vercel, where the production app currently lives, `api/github/webhooks.js` loads `app.js` and receives GitHub's webhooks at `/api/github/webhooks`.

These are the files you'll work with most often:

| Path                           | What it does                                                                                                  |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| `app.js`                       | Registers the event handlers, catches errors and sends the reply                                              |
| `lib/parse-comment.js`         | Reads the comment text and works out who to add and for which contributions                                   |
| `lib/add-contributor.js`       | Adds one contributor: looks up the user, updates the config and files, then opens or updates the pull request |
| `lib/modules/config.js`        | Reads, validates and updates `.all-contributorsrc`                                                            |
| `lib/modules/content-files.js` | Fetches the files that hold the contributors table (up to 25) and regenerates them                            |
| `lib/modules/repository.js`    | Talks to the GitHub API: reads files, creates branches, commits and opens pull requests                       |
| `lib/modules/errors.js`        | Defines the app's own errors. Their messages are shown to the user, while other errors get a generic reply    |

When someone leaves a comment that mentions the bot (`@all-contributors` or `@allcontributors`, followed by a space), the app first reads the comment to work out which GitHub usernames to add and for which contributions. It stops early and replies with a hint in two cases:

- The comment doesn't ask to add anyone. The reply shows the basic usage.
- The app can't find any valid contributions. The reply links to the list of contribution types.

Otherwise, the app goes through these steps for each username in the comment:

1. **Find or create a branch.** If a branch called `all-contributors/add-<username>` already exists, the app adds its commits to that branch. If not, it creates that branch from your default branch.
2. **Load the configuration.** The app reads `.all-contributorsrc`. If the file doesn't exist yet, it creates one with default settings and adds the badge and the contributors table to your files.
3. **Look up the contributor on GitHub.** If the username doesn't exist, the app replies with an error. If the person already has every contribution requested, the app says so and moves on to the next person.
4. **Update the files and open a pull request.** The app adds the contributions, regenerates every file listed under `files` in the configuration, and commits the changes to the branch. Then it opens a pull request against your default branch, or links to the one that's already open.

At the end, the app posts a single reply to the comment, with one line for each person, such as a link to the pull request.

If something fails along the way, the app still posts that reply, and it tries to explain what went wrong:

- **Problems the app expects**, such as a username that doesn't exist or an `.all-contributorsrc` file with invalid JSON, get a specific message that tells you what to fix. These errors are defined in `lib/modules/errors.js`.
- **Anything else** gets a generic "We had trouble processing your request. Please try again later." The real error only shows up in the app's logs.

## Run the app on your computer

Test your changes on your own copy of the app, not the production app. You'll run the app on your computer, connect it to a GitHub App you create for testing, and install that app on a test repository.

:::caution[Avoid two apps answering]
If the production app is installed on the same account as your test repository, uninstall it there first. Otherwise both apps answer every comment.
:::

### Create a smee channel

GitHub can't send webhooks straight to your laptop, so you need something to forward them. We suggest using [smee.io](https://smee.io/) for this. It's free, and it forwards every GitHub delivery to the app running on your computer.

Open [smee.io](https://smee.io/), click **Start a new channel**, and copy the channel URL. You'll use it in the next two sections.

### Create a test GitHub App

<Steps>

1. Open your [developer settings](https://github.com/settings/developers) and [create a new GitHub App](https://github.com/settings/apps/new).

2. Fill in the required fields. The name must be unique on GitHub. The homepage URL can be anything.

3. Set the important fields:

   - Webhook URL: your smee channel URL
   - Webhook secret: `development`
   - Permissions: match [`app.yml`](https://github.com/all-contributors/app/blob/main/app.yml) — read and write for repository contents, issues and pull requests, and read for metadata
   - Subscribe to events: check **Issue comment**, again as in `app.yml`
   - Where can this GitHub App be installed?: **Only on this account**

   ![The GitHub App form with “Only on this account” selected for where the app can be installed.](@/assets/project/maintain/where-can-this-app-be-installed.png)

4. Click **Create GitHub App**. You'll land on the app's settings page.

   ![The GitHub App settings page after creating a test app, showing the App ID and private key section.](@/assets/project/maintain/app-created.png)

5. On the **General** tab, note the **App ID**. Then click **Generate a private key** and save the `.pem` file, for example as `allcontributorsbot.pem`.

6. On the **Install App** tab, install the app on your account and pick a test repository with issues and pull requests enabled.

</Steps>

### Set up your `.env` file

In your clone of the [app repository](https://github.com/all-contributors/app), create a `.env` file:

```properties
APP_ID=
WEBHOOK_SECRET=development
PRIVATE_KEY=
WEBHOOK_PROXY_URL=
```

- `APP_ID`: the App ID from the **General** tab of your test app
- `WEBHOOK_SECRET`: leave as `development`, the value you set when you created the app
- `PRIVATE_KEY`: the `.pem` file encoded as one line of base64. On macOS, `openssl base64 < allcontributorsbot.pem | tr -d '\n' | pbcopy` copies it to your clipboard
- `WEBHOOK_PROXY_URL`: your smee channel URL

### Start the app and try it

<Steps>

1. Install the dependencies and start the app:

   ```sh
   pnpm install
   pnpm start
   ```

2. In your test repository, open an issue and comment `@all-contributors please add @your-username for doc`.

3. Check your terminal for the delivery, then check the issue for the app's reply.

</Steps>

<details>
<summary>Optional: replay a delivery without smee</summary>

You can skip smee and send each webhook yourself. That works, but you have to copy a payload and its headers for every test comment, so smee is usually easier.

1. Post a comment that mentions the app in your test repository.
2. Open your [app settings](https://github.com/settings/apps/), go to the **Advanced** tab, and open the most recent delivery. It should look like this:

   ![A GitHub webhook delivery for an issue_comment event, with the payload and headers shown.](@/assets/project/maintain/delivery-comment.png)

3. Save the payload as `test-webhook-payload.json`. Leave `WEBHOOK_PROXY_URL` out of `.env`, then run `pnpm install` and `pnpm start`.
4. Post the delivery to `http://localhost:3000/` with `curl` or Postman. Replace the header values below with the ones from your delivery:

   ```sh
   curl -vX POST http://localhost:3000/ -d @test-webhook-payload.json \
   ```

## Run the tests

The tests use [Vitest](https://vitest.dev/). The integration tests replay a comment against a mocked GitHub API with `nock`, using the payloads in `test/fixtures` and snapshots of the requests the app makes. The unit tests cover the parser, the configuration and the helpers.

```sh
pnpm test
```

Locally, this starts Vitest in watch mode, so it reruns the tests every time you save a file. Press `q` to stop it. To run the tests once and get a coverage report, as CI does, run `pnpm test --run --coverage`.

`pnpm lint` runs ESLint, and `pnpm format` runs the formatter (oxfmt). The `CI` workflow in `.github/workflows/ci.yml` runs format, lint, and test jobs on every push to `main` and on every pull request, and the test job runs `pnpm test --coverage` and uploads the report to Codecov. Use Node.js 24 locally so you match the `engines` field in `package.json` and the version the setup action installs in CI.

## Release and deploy

The `Release` workflow runs [semantic-release](https://github.com/semantic-release/semantic-release) on every push to `master` branch. It derives the version and the release notes from the commit messages, which is why the [commit messages](/en/project/contributing/guidelines#write-your-commit-messages) follow Conventional Commits. The package is marked private, so it isn't published to npm.

The live app still runs on Vercel today. The webhook entry point is `api/github/webhooks.js`. Vercel deploys from the `master` branch, and the current maintainers do not have access to the Vercel project settings. So a change that should go live needs both branches:

1. Merge the pull request into `main` (CI, semantic-release, and the default branch for development).
2. Push or fast-forward `master` to match `main`, which is what triggers the production deploy on Vercel.

:::caution[We are moving the app off Vercel]
We are moving the production app from Vercel to another server, because we no longer have access to the Vercel project. The release steps above are temporary. Once the new host is live, we will update this page with the real deploy process and drop the extra push to `master`.
:::
