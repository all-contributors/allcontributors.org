This page is for people who want to work on the code of the [All Contributors app](https://github.com/all-contributors/app), whether to fix a bug, to add a feature or to keep it running. If you only want to use the app, read the [app documentation](/en/app) instead. The page starts with how the app is built, then shows how to run it against a test repository, and ends with testing, releases and deployment.

## How the app is built

The app is a [Probot](https://probot.github.io/docs/) application written in JavaScript. Probot receives the webhooks that GitHub sends, verifies them and authenticates requests to the GitHub API, so the code in the repository only contains what is specific to All Contributors. The app also uses the [all-contributors-cli](https://github.com/all-contributors/cli) package as a library to edit the configuration and to generate the table, which is why a bug in the generated table can live in the CLI repository.

The entry point is `app.js`. It listens for every `issue_comment.created` webhook from repositories where the app is installed, then decides what to do with it. The `installation` and `installation_repositories` events are only written to the log. On the hosting platform, `api/github/webhooks.js` wraps the same app in a Node.js middleware that serves webhooks at `/api/github/webhooks`.

| Path | What it does |
| --- | --- |
| `app.js` | Registers the event handlers and sends the reply |
| `lib/process-issue-comment.js` | The main flow for one comment |
| `lib/parse-comment.js` | Works out the contributors and the contributions from the text of a comment |
| `lib/modules/config.js` | Reads, validates and updates `.all-contributorsrc` |
| `lib/modules/content-files.js` | Fetches the files that hold the table and regenerates them |
| `lib/modules/repository.js` | Reads and writes files, creates branches and opens pull requests through the GitHub API |
| `lib/modules/comment-reply.js` | Collects the replies and posts them as one comment |
| `lib/modules/errors.js` | The errors whose messages are shown to the user |

### What happens to a comment

Every new issue or pull request comment in an installed repository is delivered to the app as a webhook. The handler in `app.js` then returns early if `allcontributors[bot]` wrote the comment, or if the comment does not include `@all-contributors` or `@allcontributors` followed by a space. Otherwise it parses the comment, and for each contributor it finds, it takes these steps:

1. It checks whether the branch `all-contributors/add-<username>` already exists. If it does, the app works from that branch, and otherwise it starts from the default branch.
2. It loads `.all-contributorsrc`. If the file doesn't exist, the app starts from its default configuration, which also makes it add the badge and the list to the files.
3. It looks up the user on GitHub and adds the contributions. If the person already has all of them, the app replies and stops.
4. It regenerates the files listed under `files`, commits each changed file to the branch, and opens a pull request or finds the one that is already open.
5. It posts one reply with the results for all contributors. If something fails, the reply contains the message of the error when it is one of the app's own errors.

[Comment syntax](/en/app/reference/comment-syntax) and [Troubleshooting](/en/app/guides/troubleshooting) describe the same flow from the user's side.

## Run the app on your computer

To try a change, you run the app on your machine and connect it to a GitHub App that you create for testing. The production app sends webhooks to the live deployment, so you can't point it at your laptop, and you wouldn't want a local build answering in real repositories. Uninstall the production app from your account first. Otherwise two apps answer every comment.

### Create a GitHub App for testing

<Steps>

1. Open your [developer settings](https://github.com/settings/developers) and [create a new GitHub App](https://github.com/settings/apps/new).

2. Fill in the required fields. The name must be unique on GitHub. The homepage URL and webhook URL can be anything for now.

3. Set the important fields:

   - Webhook secret: `development`
   - Permissions: match [`app.yml`](https://github.com/all-contributors/app/blob/main/app.yml) — read and write for repository contents, issues and pull requests, and read for metadata
   - Subscribe to events: check **Issue comment**, again as in `app.yml`
   - Where can this GitHub App be installed?: **Only on this account**

   ![The GitHub App form with “Only on this account” selected for where the app can be installed.](@/assets/project/maintain/where-can-this-app-be-installed.png)

</Steps>

### Configure the GitHub App

You should now have an app created.

![The GitHub App settings page after creating a test app, showing the App ID and private key section.](@/assets/project/maintain/app-created.png)

<Steps>

1. On the **General** tab, click **Generate a private key** and download the `.pem` file. Name it something like `allcontributorsbot.pem`.

2. On the **Install App** tab, install the app on your own account, on a test repository with issues and pull requests enabled.

</Steps>

### Configure your local environment

In your clone of the app repository, create a `.env` file:

```properties
APP_ID=
WEBHOOK_SECRET=development
PRIVATE_KEY=
WEBHOOK_PROXY_URL=
```

- `APP_ID`: from the General tab of your test app
- `WEBHOOK_SECRET`: leave as `development` (the value you set when you created the app)
- `PRIVATE_KEY`: encode the `.pem` file as one line of base64 and paste it here. On macOS you can run `openssl base64 < allcontributorsbot.pem | tr -d '\n' | pbcopy` to copy it to the clipboard
- `WEBHOOK_PROXY_URL`: a channel URL from [smee.io](https://smee.io/) (see below)

### Forward webhooks with smee.io

We suggest you use [smee.io](https://smee.io/). It is free, and it forwards every GitHub delivery to your laptop so you can comment on an issue and see the app respond without posting webhooks by hand.

<Steps>

1. Create a channel on [smee.io](https://smee.io/) and paste its URL into `.env` as `WEBHOOK_PROXY_URL`.

2. Set the same URL as the webhook URL of your test GitHub App.

3. Install the dependencies and start the app:

   ```sh
   pnpm install
   pnpm start
   ```

4. In a test repository under the account where you installed the app, open an issue and comment `@all-contributors please add @your-username for doc`. The log in your terminal shows the delivery, and a reply appears on the issue.

</Steps>

:::note[Replay a delivery without smee]
You can skip smee and send each webhook yourself. That works, but you have to copy a payload and its headers for every test comment, so smee is usually easier.

1. Create a test repository, enable issues and pull requests, open an issue, and post a comment that mentions the app.
2. Open your [app settings](https://github.com/settings/apps/), go to the **Advanced** tab, and open the most recent delivery. It should look like this:

   ![A GitHub webhook delivery for an issue_comment event, with the payload and headers shown.](@/assets/project/maintain/delivery-comment.png)

3. Save the payload as `test-webhook-payload.json`. Leave `WEBHOOK_PROXY_URL` out of `.env`, then run `pnpm install` and `pnpm start`.
4. Post the delivery to `http://localhost:3000/` with `curl` or Postman. Replace the header values with the ones from your delivery. With `curl`, that looks something like this:

   ```sh
   curl -vX POST http://localhost:3000/ -d @test-webhook-payload.json \
   --header "Content-Type: application/json" \
   --header "User-Agent: GitHub-Hookshot/4d63832" \
   --header "X-GitHub-Delivery: 413857f0-8b61-11eb-92be-566b7aa5f6ee" \
   --header "X-GitHub-Event: issue_comment" \
   --header "X-GitHub-Hook-ID: 297478976" \
   --header "X-GitHub-Hook-Installation-Target-ID: 105785" \
   --header "X-GitHub-Hook-Installation-Target-Type: integration" \
   --header "X-Hub-Signature: sha1=ed222e6750dc2954a422ed8dd371f9da66368104" \
   --header "X-Hub-Signature-256: sha256=04d0943f20545ac8df974466c502e4b9743d3618149b03f4ea1a9e658bf31fd0"
   ```

5. If the terminal shows no errors, check your test issue for the reply.
:::

## Test the app

The tests use [Vitest](https://vitest.dev/). The integration tests replay a comment against a mocked GitHub API with `nock`, using the payloads in `test/fixtures` and snapshots of the requests the app makes. The unit tests cover the parser, the configuration and the helpers.

```sh
pnpm test
```

The command also writes a coverage report. `pnpm lint` runs ESLint, and `pnpm format` runs the formatter (oxfmt). The `CI` workflow in `.github/workflows/ci.yml` runs format, lint, and test jobs on every push to `main` and on every pull request, and the test job uploads coverage to Codecov. Use Node.js 24 locally so you match the `engines` field in `package.json` and the version the setup action installs in CI.

## Release and deploy

The `Release` workflow runs [semantic-release](https://github.com/semantic-release/semantic-release) on every push to `main`. It derives the version and the release notes from the commit messages, which is why the [commit messages](/en/project/contributing/guidelines#write-your-commit-messages) follow Conventional Commits. The package is marked private, so it isn't published to npm.

The live app still runs on Vercel today. The webhook entry point is `api/github/webhooks.js`. Vercel deploys from the `master` branch, and the current maintainers do not have access to the Vercel project settings. So a change that should go live needs both branches:

1. Merge the pull request into `main` (CI, semantic-release, and the default branch for development).
2. Push or fast-forward `master` to match `main`, which is what triggers the production deploy on Vercel.

:::caution[We are moving the app off Vercel]
We are moving the production app from Vercel to another server, because we no longer have access to the Vercel project. The release steps above are temporary. Once the new host is live, we will update this page with the real deploy process and drop the extra push to `master`.
:::
