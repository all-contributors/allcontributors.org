All Contributors is maintained by volunteers, and help of every size is welcome, from fixing a typo to reviewing a feature. This page helps you find where to start. Everyone who takes part is expected to follow the [code of conduct](/en/project/contributing/code-of-conduct).

## Ways to help

Which kind of help fits you depends on what you like to do:

- Improve these pages, for example by fixing a mistake, clarifying an explanation or adding something that was missing. [Improve the documentation](/en/project/contributing/documentation) explains how to do it and how to preview your changes.
- Fix a bug or add a feature to the app or the CLI. Each of them has its own repository, and [Maintaining the app](/en/project/maintaining/app) and [Maintaining the CLI](/en/project/maintaining/cli) explain how to run and test them.
- Report a problem or suggest an idea by opening an issue in the repository that it belongs to. [Repositories](/en/project/about/repositories) tells you which one that is.
- Review pull requests, answer questions in issues, or help organize the project. These are contributions too, and you can be recognized for them.

If you aren't sure where something belongs, open an issue in the [documentation repository](https://github.com/all-contributors/allcontributors.org/issues) and describe what you have in mind.

## Open a pull request

Whichever repository you work in, the process is the same. Fork the repository, create a branch for your change, commit it and open a pull request against the default branch. A pull request from a branch in your own fork is how every change reaches the project, except automated updates such as dependency bumps and the pull requests that the app opens to add contributors.

Keep the pull request focused on one change, and link the issue it relates to if there is one. For larger changes, open an issue first and discuss the design there, so that you don't spend time on something the maintainers would want to approach differently. The [maintainer processes](/en/project/maintaining/processes) describe what happens to your pull request after you open it.

## Write your commit messages

The projects use [Conventional Commits](https://www.conventionalcommits.org/) for pull request titles and commit messages. Maintainers squash a pull request into one commit when they merge it, and tools build changelogs and releases from those commit messages. A message has a type, an optional scope and a short description:

```none
fix(parser): handle empty strings correctly
docs: update the installation instructions
feat(api): add support for custom headers
```

If you would rather be guided, run `pnpm commit` in this repository, or `npm run commit` in the CLI repository, and answer the questions it asks.

## Add yourself as a contributor

Everyone who helps is recognized in the contributors table of the repository they worked on. Maintainers add you after they merge your pull request, and you can also ask for it yourself by commenting `@all-contributors please add @your-username for doc` on the issue or pull request, replacing `doc` with the type that fits. See [Add contributors](/en/app/guides/usage) for the details.
