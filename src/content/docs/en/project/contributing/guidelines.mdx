## All Contributors AI contribution policy

:::note
**AI contribution policy summary**

* You can use AI tools to write code, support docs, or explore ideas
* Write comments, issues, and pull request descriptions in your own voice
* Understand your contributions and be able to explain them in your own words
* AI agents may not open issues or pull requests, or talk to us directly
* Do not use our project to train AI agents
* Keep contributions small, focused, and tied to an existing issue
* Open one pull request at a time and use our issue and pull request templates
:::

This project **welcomes the thoughtful use of AI tools** when contributing. We
have found that low-quality AI-generated content takes maintainers more time to
read, understand, and respond to. To keep review sustainable, we ask all
contributors to follow the principles below.

### 1. Communicate in your own voice

When we read a comment, issue, or pull request from you, we want to know we are
reading your words. We value clear, human communication over perfect grammar or
spelling. Please:

* Write all comments, issues, and pull request descriptions yourself
* Avoid pasting AI-generated summaries that don't reflect your own
  understanding of what you are contributing

### 2. Understand what you submit

Many of us use AI in our open source work, and we support using it to
understand our projects, generate code and docs, and explore ideas. However,
**you must understand what the AI tool produced and be able to describe it
before you submit it to us.** Contributions should reflect your own reasoning
and problem solving.

### 3. Keep contributions focused and easy to review

* **Start with an issue.** Every pull request must address an open issue. If
  one doesn't exist, open an issue first and wait for maintainer feedback.
* **Scope tightly.** Each pull request should do one thing so that it is easy
  for us to review.
* **Don't batch.** Do not open multiple issues or pull requests at once.
* **One pull request at a time.** Please have no more than one open pull
  request. Once it is merged or closed, you can open another. If you are a
  regular contributor, a maintainer may agree to a higher limit.
* **Use our templates.** Fill out the issue and pull request templates
  completely. Please don't delete them or remove sections.

### What we do not allow

* **Agent-driven contributions.** AI agents may not open pull requests or
  issues, or communicate with us directly. A human must open and manage every
  contribution.
* **Training on our project.** Do not use our repositories, issues, or reviews
  to train AI agents or models.

### How we respond

* If you delete our issue or pull request templates, we will close the pull
  request immediately.
* If a pull request doesn't link to an open issue, we will close it and ask you
  to open an issue first.
* If you open multiple pull requests at once, we will close all but the oldest.
* If we suspect agent-driven contributions or use of our project to train
  agents, we may block the account without warning.

This policy is based on the
[Human Voice policy, version 1.0.0](https://ai-policy.dev/policies/human-voice/1.0.0)
from 2026-09-23. Read more about this and other AI contribution policies on
[ai-policy.dev](https://ai-policy.dev/).

## How to commit

We use the [angular commit convention](https://github.com/angular/angular/blob/main/CONTRIBUTING.md#-commit-message-guidelines) for commits that are used for an automated changelog generation, so it would be advisable to respect that.
If you're not used to it or are afraid to mistype a commit, you can run `npm run commit` or `git cz` (if you have installed `commitizen`) which would take you through a few questions and write the commit for you.

## Editing Content

:::tip
Every page has an _Edit_ button up the bottom, clicking this will take you straight to the GitHub source code for that page.
:::

Once on a file, click the 'pencil' icon to [easily edit the file inline](https://help.github.com/articles/editing-files-in-your-repository/).
After making your changes, create a commit with your changes. You will want to create and commit these changes on a **new branch** in your fork of the repository.

After committing your changes, you can create a pull request to propose your changes to be merged into the main branch.

## Translations

[![Crowdin](https://d322cqt584bo4o.cloudfront.net/all-contributors/localized.svg)](https://crowdin.com/project/all-contributors)

Our translations are managed through crowdin. You can help contribute by heading to [the crowdin project] and suggesting translations.
If you like, [comment on this issue](https://github.com/all-contributors/allcontributors.org/issues/143) to let us know you're helping or if you have any queries!

> When translating, anything that has the [XPATH](https://developer.mozilla.org/en-US/docs/Web/XPath) `@href`, `@src` etc mustn't be translated. Things like `code` should not be either. This will cause the project to 404. See the below image for an example:

![A screenshot that shows the GitHub interface with a file open focused on the pencil icon that allows you to edit the page.](@/assets/project/translating-xpath.png)

> However, it's recommended to translate any content that would contribute to a better comprehension like the comments in `code` tags _as long as_ it doesn't change the actual code since it only understands English.

### How to's

#### Login to Crowdin

1. Go to [the crowdin project], then [sign up](https://crowdin.com/join) and/or [log in](https://crowdin.com/login).
2. Join the "All Contributors" project and voila!

#### Translate strings

1. Go to [the crowdin project].
2. Click on the flag of the language you want to translate the documentation to.
3. Click on any `*.md` files that aren't completely translated (read showing 100% on the right-hand side)
4. Write your translation in the _"Enter translation here"_ field (which would correspond to the translation of the text in the _"SOURCE STRING"_ field above) then click "SAVE"
5. For **proofreaders** only: You can either approve translation suggestions (whether it's done by you or someone else), which you will find in the _"[LANGUAGE] TRANSLATIONS"_ section, by clicking on the :ballot_box_with_check: or delete them by clicking on the :wastebasket: icon.

### Change deployments

After you translate strings in any given language, you won't see those changes appearing live until the `main` branch was updated followed by a successful deployment.

## Run the website locally

All Contributors currently uses [Astro](https://docs.astro.build/) with [Starlight](https://starlight.astro.build/) for our documentation and website.

To build the docs locally:

<Steps>

1. Make sure `npm` is installed on your machine. Use the [nodejs documentation](https://docs.npmjs.com/downloading-and-installing-node-js-and-npm) if you aren't sure how to install `npm`.

    To check that npm is installed run the following in your favorite shell:

    ```sh
    npm -v
    ```

2. Next, make sure you have at least node version 0.22 (LTS) or higher. To check the version, use:

    ```sh
    node -v
    ```

    If you don't have atleast version `.22` or higher, please install node or upgrade your current version.

3. Install all dependencies:

    <Tabs syncKey="pkg">
    <TabItem label="npm">

    ```sh
    npm i
    ```

    </TabItem>
    <TabItem label="pnpm">

    ```sh
    pnpm i
    ```

    </TabItem>
    <TabItem label="Yarn">

    ```sh
    yarn i
    ```

    </TabItem>
    </Tabs>

4. Once you have completed the above, you can launch a server locally that will build and run the docs locally. In your favorite shell run:

    <Tabs syncKey="pkg">
    <TabItem label="npm">

    ```sh
    npm run start
    ```

    </TabItem>
    <TabItem label="pnpm">

    ```sh
    pnpm start
    ```

    </TabItem>
    <TabItem label="Yarn">

    ```sh
    yarn start
    ```

    </TabItem>
    </Tabs>

5. Then, go to `http://localhost:4321` and you will see the all contributors website there!

</Steps>

Refresh the browser page as needed when editing markdown pages.

### Checking links

We use [Lychee](https://lychee.cli.rs/) to validate all links within the repository. This ensures that we don't include any links that lead to broken pages.

If you want to run the link-check locally, run the following command:

<Tabs syncKey="pkg">
<TabItem label="npm">

```sh
npm run link-check
```

</TabItem>
<TabItem label="pnpm">

```sh
pnpm link-check
```

</TabItem>
<TabItem label="Yarn">

```sh
yarn link-check
```

</TabItem>
</Tabs>

If your changes introduced any broken links, Lychee will tell you which links you have to fix in the output.
