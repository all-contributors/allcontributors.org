A contributors table only helps if it is current and if it includes the people whose work is easy to overlook. These tips are for maintainers who want to keep the table healthy, and they apply whichever tool you use to update it.

## When to add a contributor

Add someone as soon as you notice their contribution. A contribution that is added later is easy to overlook when the list finally gets updated, so the sooner you add the person, the less likely it is that their effort gets missed. This can be hard for contributions that don't show up as a commit, such as answering questions or organizing an event, but try to keep the time between the contribution and the update short.

With the [app](/en/app), recognizing a contribution takes one comment on the issue or pull request where it happened. For example:

> `@all-contributors please add @tbenning for design`

## Encourage people to add themselves

As the owner or a maintainer you are not the only person responsible for the table. Contributors can ask for their own recognition with the app, and the more of them do, the less work it is for you. A comment on the issue, the blog post or the answer that invites the person to add themselves is often enough, and a direct message works too when that fits the situation better.

Many contributors don't realize that their work counts. They may not have read what the specification says a contributor is, or they may feel their contribution is too small. Encourage them anyway, and if they still hesitate, you can add them yourself. In that case, do it in a pull request so that they can check that they are happy to be listed.

There are no hard rules for when a contribution belongs in the table. The specification recommends against excluding people because of how big their contribution seems, so when in doubt, add the person and be fair about it.
